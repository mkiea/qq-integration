## 二、S4 的真实形态（本机实测，改变了它的性质）

它把"入站本地路径"列为 **P0**。实测：`qq-inbox.jsonl` 里 1215 条入站帧，`file` 字段
**全部是纯文件名**（形如 `2A24C…jpg`、`123.txt`），**没有一条是绝对路径**。

而 `bridge.js:4876` 的过滤条件是 `/^([a-zA-Z]:[\\/]|\/)/`（必须以盘符或 `/` 开头）
⇒ **正常流量下 `localPaths` 是空数组，这个分支从未被执行过**。

所以正确描述不是"现在能读任意文件"，而是：

- **正常流量不可达** ⇒ 直接风险低
- 但**正因为不可达，这条路没有实战检验**，改动时更容易踩空
- 攻击面成立的前提是"OneBot 端可被伪造"——而这正好是 **S1 + S2**

## 三、真正要害的地方：单看每条都有前提，串起来就没有前提了

```
恶意网页
  → new WebSocket('ws://127.0.0.1:6700')     ← 浏览器不受同源策略限制，会带 Origin
  → S1/S2：没 token、不查 Origin，连接被接受
  → 发一条伪造的群消息事件，file 字段填任意本地路径
  → S4：readFileSync 直接读
  → 内容进 Agent 上下文 → 诱导它复述 → 发到群里
```

这条链**每一步都只是一行代码的疏忽**，但串起来就成了"网页能读本机文件并外发"。
拆开看每一条都能说"前置条件不成立"，合起来就不成立了。

它这份报告最有价值的一句判断是：

> 你对 Agent 出站文件访问的约束已经相当严格，却还没有把相同等级的信任边界
> 完整覆盖到 OneBot 连接身份和入站本地文件读取。

这条**结构性判断是准的**，而且它自己没意识到这恰好是我这边一直在记的那类缺陷：
**同一套策略只盖住了部分路径，缺失的地方不报错**。
S2（控制台有 Origin 校验、OneBot 没有）、S5（媒体下载有闸、群文件没有）、
S4（URL 有闸、本地路径没有）——**三条都是同一个形状**。

## 四、我不同意 / 要下调的地方

| 它的判断 | 我的判断 | 理由 |
|---|---|---|
| S4 列 P0 | 下调到 **P2** | 正常流量不可达（§二）。它没有本机的入站录制，只能从代码推断，这一步推断不成立 |
| `send.js` 的 TOCTOU 竞争 | **P3，且不建议现在做** | 能在"校验后、发送前"替换文件，说明本机已有代码执行能力——那时游戏已经结束。修它买不到安全，只买到复杂度 |
| 默认白名单含 `localhost` / `127.0.0.1` 是缺陷 | **是权衡不是缺陷** | 本地模型（11434）、edge-tts 都在回环地址上；删了会直接打死本地模型与语音。要做只能做成可关开关，默认不能关 |
| "先别改代码，保留 alpha-1 作基准" | **同意，但理由不同** | 它认为要先补测试；我认为更要紧的是：**S5 不修就是一个现成的洞**，而它不需要任何设计权衡（白名单已含 `qq.com` / `qq.com.cn` / `myqcloud.com`） |

## 五、它说得对、值得采纳的方法论

1. **安全测试分两类**：显式攻击（"忽略规则"/"泄露记忆"）与**隐式攻击**（多轮正常对话渐进改变行为）。
   后者才是难的，而现有 `taint.js` 只覆盖前者。
2. **干净环境测试**：Windows Sandbox 或全新虚拟机，每轮从快照恢复——否则"我这儿能装"可能只是
   别的软件早就把依赖准备好了。它明确点出了本项目的 schemastery 例子。
3. **三个验收维度**：安全性 / 可靠性 / 可部署性，缺一不可。
4. **不要把安装失败全归成用户操作错误**：需要开终端、建 junction、改 `package.json`、理解
   `peerDependencies` 才能装上，即使步骤正确，体验仍有问题。建议做安装诊断器。
5. 它对测试的态度是诚实的：明确写了"缺依赖跑不全，**不能视为完整通过**"——
   没有像常见报告那样把"我看了目录"说成"我跑过了"。
