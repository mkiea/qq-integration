## 二、S4 的真实形态（本机实测，改变了它的性质）

它把"入站本地路径"列为 **P0**。实测：`qq-inbox.jsonl` 里 1215 条入站帧，`file` 字段
**全部是纯文件名**（形如 `2A24C…jpg`、`123.txt`），**没有一条是绝对路径**。

而 `bridge.js:4876` 的过滤条件是 `/^([a-zA-Z]:[\\/]|\/)/`（必须以盘符或 `/` 开头）
⇒ **正常流量下 `localPaths` 是空数组，这个分支从未被执行过**。

所以正确描述不是"现在能读任意文件"，而是：

- **正常流量不可达** ⇒ 直接风险低
- 但**正因为不可达，这条路没有实战检验**，改动时更容易踩空
- 攻击面成立的前提是"OneBot 端可被伪造"——而这正好是 **S1 + S2**

## 三、真正要害的地方：单看每条都有前提，串起来就没有前提了

```
恶意网页
  → new WebSocket('ws://127.0.0.1:6700')     ← 浏览器不受同源策略限制，会带 Origin
  → S1/S2：没 token、不查 Origin，连接被接受
  → 发一条伪造的群消息事件，file 字段填任意本地路径
  → S4：readFileSync 直接读
  → 内容进 Agent 上下文 → 诱导它复述 → 发到群里
```

这条链**每一步都只是一行代码的疏忽**，但串起来就成了"网页能读本机文件并外发"。
拆开看每一条都能说"前置条件不成立"，合起来就不成立了。

它这份报告最有价值的一句判断是：

> 你对 Agent 出站文件访问的约束已经相当严格，却还没有把相同等级的信任边界
> 完整覆盖到 OneBot 连接身份和入站本地文件读取。

这条**结构性判断是准的**，而且它自己没意识到这恰好是我这边一直在记的那类缺陷：
**同一套策略只盖住了部分路径，缺失的地方不报错**。
S2（控制台有 Origin 校验、OneBot 没有）、S5（媒体下载有闸、群文件没有）、
S4（URL 有闸、本地路径没有）——**三条都是同一个形状**。

## 五、它说得对、值得采纳的方法论

1. **安全测试分两类**：显式攻击（"忽略规则"/"泄露记忆"）与**隐式攻击**（多轮正常对话渐进改变行为）。
   后者才是难的，而现有 `taint.js` 只覆盖前者。
2. **干净环境测试**：Windows Sandbox 或全新虚拟机，每轮从快照恢复——否则"我这儿能装"可能只是
   别的软件早就把依赖准备好了。它明确点出了本项目的 schemastery 例子。
3. **三个验收维度**：安全性 / 可靠性 / 可部署性，缺一不可。
4. **不要把安装失败全归成用户操作错误**：需要开终端、建 junction、改 `package.json`、理解
   `peerDependencies` 才能装上，即使步骤正确，体验仍有问题。建议做安装诊断器。
5. 它对测试的态度是诚实的：明确写了"缺依赖跑不全，**不能视为完整通过**"——
   没有像常见报告那样把"我看了目录"说成"我跑过了"。

## 七、怎么修的：一个函数，不是三处补丁

S3 / S5 / S6 **不是三个独立的洞，是同一个结构问题**：下载逻辑散在三处，各写了一遍
`fetch` ——群里 `/取`、入站图片/语音、`get_file` 回退。结果是只有两处加了白名单、
三处全都是「先整包读进内存再比大小」。**同一个策略写三遍，必然漏一遍**；而且下次再加
一条下载路径还会漏。

所以没有逐处打补丁，而是抽了一个 `fetchGuarded(url, { maxBytes, timeoutMs })`：

- 每一跳都过 `assertEgress`（S3）
- 用流的 reader 边读边累加，超 `maxBytes` 立刻 `abort`（S6）
- 超时是**整个下载**的总时限，不是每跳重置（顺带挡住 slowloris）
- 三处调用点全部换掉（S5 就是这么消失的）

S1/S2 单独处理：`#accept` 里加 Origin 闸，默认拒绝带 `Origin` 的连接。
`accessToken` 为空时**在开始监听之前**就告警——不是等第一条连接进来才说，
因为端口一开就已经暴露了，等有人连等于把"一直没人来"这段静默掉。

## 八、对抗测试：为什么必须有正例

只测「恶意输入被拒」是没用的——一个恒 `return false` 的假实现能全过。所以两组测试
都是正反同时验：

`test/egress-guard-unit.mjs`（22 条，真起本地 HTTP 服务）
- 陌生域名被拒 **且一次请求都没发**（用 `fetchImpl` 探针数次数：拒绝发生在连接之前）
- 302 跳到 `169.254.169.254` 被拒，**且被拒的是第二跳**（第一跳确实请求过）
- **相对跳转 / 两跳链仍然走得通**（否则等于把所有重定向都打死）
- 无限自我重定向在 `maxRedirects` 停
- 超限时 **服务端一共只写出 0.6MiB**（`maxBytes` 是 512KiB）——这条才区分得出
  「真流式」和「假流式」：假实现会一直发到测试自己超时
- 慢速响应在 `timeoutMs` 附近被掐断（306ms vs 300ms）

`test/onebot-origin-unit.mjs`（14 条，真起 WS 服务、真连）
- 带 `Origin` 被 4003 关掉；**不带 `Origin` 的连接完全正常**（NapCat/Waylay 就长这样）
- 连**本机网页**的 Origin 也拒（攻击者可以自己起一个本地页面）
- `allowBrowserOrigin: true` 后带 Origin 能连（证明开关不是死代码）
- 有 token 且带 Origin：**token 正确也不放浏览器进来**
- 端口一开就提示未配置 token（不连任何客户端时也检查这一条）

## 九、体检工具与"干净环境"的真实边界

`tools/doctor.mjs`：一条命令分 A（安装）/ B（连通）两区报告，每项失败给可复制执行的
修复命令，`--json` 可贴回反馈。

`test/doctor-unit.mjs`（14 条）钉的是一件关键事：**在什么都没装的环境里它必须报 FAIL**。
用空的 `DSH_HOME` 模拟，并且把「连 profile 目录都没有」和「有 profile 但没装插件」分成
两条断言——前者该说"DSH 没跑过"，后者才该给 `dsh plugin`。混在一起会逼工具给出
不合场景的建议。

⚠️ **本机做不了真正的虚拟机安装测试**（2026-10-31 实测）：`wsl.exe` 被安全策略封禁
（不可绕过）、Hyper-V / Windows Sandbox 查询需管理员提权、没有 VirtualBox / VMware。
所以「干净环境」只能降到"干净 profile"这一层，**测不到**的包括：全新 Windows 缺
VC++ 运行时、缺 Node、路径含中文或空格、非管理员账户、杀软拦截。
这部分要靠别人在真机上跑 `node tools/doctor.mjs` 反馈——这也是它带 `--json` 的原因。
